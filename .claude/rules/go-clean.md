# Правила сервиса go-clean

Договор с панелью — в `CLAUDE.md`, здесь — как писать код и `paas.toml`, чтобы его не нарушить. Пошаговые рецепты — скил `go-clean`. Подробности и «почему» — `ARCHITECTURE.md`.

## Слои

Поток вызова: `handler → usecase → service → repository → Postgres`; к внешнему API — `service → client → внешний API`.

- Зависимость идёт только вниз. Каждый пакет описывает нужное ему от соседей локальными интерфейсами в своём `deps.go`; конкретные типы встречаются только в `cmd/*/main.go`.
- Точки входа: `cmd/api` — API `/api/v1/<группа>.<действие>`; `cmd/workers/<имя>` — воркеры; `cmd/cron/<имя>` — задачи по расписанию. Других папок в `cmd/` не заводим: сборка и панель их не увидят.
- Сборка — вручную в `main.go`, снизу вверх: база → clients → repositories → services → usecases → handlers → webserver. Импорт с алиасом `<camelName><Layer>` (`greeterService`, `createGreetingUsecase`), переменная — `<camelName><Repo|Cl|Svc|Case|Method>`.
- Пакет = одна единица: handler — одна операция OpenAPI, usecase — один сценарий с методом `Run`, service — один доменный механизм (`greeter`), client — один внешний API, repository — одна таблица.
- Handler зовёт service напрямую только для простого чтения без ветвлений. Валидация ввода, несколько сервисов или бизнес-ошибка — значит нужен usecase.
- Типы: `entity` — доменные модели (`Greeting`); `model` — структуры внешних систем, которые возвращают клиенты, и входные DTO usecase (`<Usecase>Params`); DTO — только сгенерированные, наружу через `internal/api/mapper`.
- Ошибки по слоям: client возвращает типизированный `APIError`; service оборачивает `fmt.Errorf("failed to <действие>: %w", err)` и объявляет sentinel `ErrXxx`; usecase переводит в `errx.Validation/NotFound/Forbidden/Internal` с `errx.WithPublicMessage("<по-русски>")`; handler переводит `errx` в HTTP-код.
- Имена функций и методов начинаются с глагола: `ListLatest`, `Add`, `parseTag`. Исключения: `New`, `Run`, `Handle`, опции и контекст `With*`, методы стандартных интерфейсов, сгенерированный код и `internal/util/webserver` (его API зашит в codegen).
- `internal/generated/` правит только `make codegen`.
- Юнит-тесты — только табличные: слайс кейсов + цикл с `t.Run(tt.name, ...)`, по одной таблице на метод. `testify` + `gomock`, моки из `deps.go` (`make generate`) в `_mocks/`. Имена кейсов — по-русски.
- Модуль Go — из первой строки `go.mod`, в рецептах скила он обозначен `<module>`.

### handler — `internal/api/**`

- Пакет `internal/api/handler/<operation_snake>`: `deps.go`, `handler.go`, `handler_test.go`, `_mocks/`. Имя пакета = имя сгенерированного пакета в `internal/generated/api/schema/`, импорт сгенерированного — с алиасом `schema`.
- HTTP-методы — только `GET` (чтение), `POST` (создание и изменение), `DELETE` (удаление). Параметры `POST` — только в JSON-теле (`requestBody`); query — для `GET` и `DELETE`.
- Путь `/api/v1/<группа>.<действие>`: веб-приложение проекта пересылает бэкенду только пути под `/api/`. Несовместимое изменение контракта — новая версия `/api/v2/...`.
- `/health` встроен в `internal/util/webserver` и всегда отвечает 200: по нему панель понимает, что сервис запущен. Свою ручку на этот путь не заводим.
- Сигнатура `Handle` — из сгенерированного `handle.go`: `schema.JsonRequest` для тела, `schema.Parameters` для path/query.
- Порядок в `Handle`: разбор запроса (`req.DTO()` / `params.Path()` / `params.Query()`; ошибка → 400 "Invalid request") → вызов usecase → маппинг ошибок → ответ.
- Ошибки: `errx.ErrValidation` → 400, `ErrNotFound` → 404, `ErrForbidden` → 403, текст — `errx.PublicMessage(err)`. Остальное: `h.log.Error(ctx, fmt.Errorf("<op> failed: %w", err))`, 500 "Internal Server Error" и `return err`. Обработанная клиентская ошибка возвращает `nil`.
- Ответ — сгенерированные типы из `components`; ошибка — `makeJSendError(msg)` (локальная функция пакета, копируется как есть). Entity → DTO — функцией в `internal/api/mapper/<name>.go`.
- Middleware (авторизация, лимиты) навешивается в `main.go` через `webserver.WithPatternMW` по `<camel>Schema.HandlerPath`.

### usecase — `internal/usecase/**`

- Пакет `internal/usecase/<verb_noun>` (глагол первым: `create_greeting`): `deps.go`, `usecase.go`, `usecase_test.go`, `_mocks/`.
- Usecase — оркестрация других слоёв, чаще всего сервисов. Своей логики хранения, SQL и HTTP в нём нет.
- `type Usecase struct` + `New(...)` + единственный публичный метод `Run(ctx, ...)`. Больше трёх входных значений — структура `<Usecase>Params` в `internal/model/<verb_noun>.go`, не в пакете usecase: иначе вызывающий слой импортирует конкретный usecase ради типа.
- Каждое крупное действие в `Run` предваряет нумерованный комментарий-шаг: `// 1. Проверяем текст`.
- Сначала валидация, которая не ходит в базу и внешние API (trim, длины в рунах, формат), потом вызовы сервисов. Лимиты — именованные константы с комментарием-«почему».
- Каждая ошибка наружу — `errx`: `Validation`/`NotFound`/`Forbidden` с `WithPublicMessage("<по-русски>")` для клиента, `errx.Internal(err)` для остального. Sentinel сервисов (`errors.Is(err, <svc>.ErrXxx)`) переводятся в `errx` здесь.
- Один публичный текст на случаи, которые нельзя различать снаружи (чужое/несуществующее), — иначе ручка становится оракулом перебора.
- Запись в несколько таблиц — в одной транзакции: `tx.Do(ctx, func(ctx context.Context) error {...})`, менеджер транзакций собирается в `main.go`.
- Зависимости в `deps.go` называются по роли: `greeter`, `<name>Client`, `logger`. Логгер — только если usecase глотает ошибку (best-effort шаг).

### service — `internal/service/**`

- Пакет `internal/service/<mechanism>` (`greeter`) — доменный механизм поверх клиентов и репозиториев. SQL здесь не пишется. Файлы: `deps.go`, `service.go`, `service_test.go`, `_mocks/`.
- Инжектятся только клиенты и репозитории. Сервис в сервис не инжектится: два сервиса связывает usecase.
- `type Service struct` + `New(...)`; настройки (TTL, лимиты) — аргументами `New` из конфига или константами пакета с комментарием-«почему», а не чтением env.
- Сервис собирает entity (вычисляемые поля, время, хеши) и прячет от usecase детали хранения. Методы — доменные глаголы (`Add`, `ListLatest`), а не CRUD репозитория.
- Ошибки: `fmt.Errorf("failed to <действие>: %w", err)`; доменные исходы — экспортируемые sentinel `var ErrXxx = errors.New("...")` с комментарием, зачем они. `errx` здесь не используется.
- «Не найдено» у внешнего API сервис переводит в свой sentinel, чтобы usecase не разбирал ошибки клиентов.
- Внешний провайдер — интерфейс в `deps.go` (`provider`), реализация выбирается в `main.go`.

### repository и entity — `internal/repository/**`, `internal/entity/**`

- Пакет `internal/repository/<table_singular>` (`note`): `repository.go` + `row.go`. Без `deps.go`, моков и юнит-тестов.
- `New(db *sqlx.DB, getter *trmsqlx.CtxGetter)`; каждый запрос идёт через `r.getter.DefaultTrOrDB(ctx, r.db)`, чтобы подхватить транзакцию из контекста. Транзакцию открывает usecase (`tx.Do`).
- SQL — только `squirrel` с `PlaceholderFormat(sq.Dollar)`. На уровне пакета: `tableName`, `tableFields`, `selectBuilder`/`insertBuilder`/`updateBuilder`.
- `row.go`: `rowEntry` с тегами `db`, метод `toEntity()`. Наружу — только `*entity.X`.
- `Get*` без результата — `(nil, nil)` (`sql.ErrNoRows` гасится). Update/Delete возвращают `(bool, error)` по `RowsAffected`. `Create` заполняет `ID`/`CreatedAt` через `RETURNING`.
- Занятое уникальное значение — `ON CONFLICT (...) DO NOTHING RETURNING id` и `(false, nil)` из `Create`, а не проверка перед вставкой: её обгонит параллельный запрос.
- Список без предела не отдаём: `Limit` из константы сервиса.
- Время — `time.Now().UTC()`. Ошибки — `failed to build <op>` / `failed to execute <op>`.
- entity (`internal/entity/<name>.go`): ID-тип `type XID int64`, enum — `type XType string` + константы, nullable и генерируемые БД поля — указатели (`ID *XID`, `CreatedAt *time.Time`). Указатель на значение — встроенным `new(выражение)`.
- Репозиторий — одна таблица. Склейку данных из двух таблиц делает service.
- База: sqlx + lib/pq, подключение в `internal/util/psql`. В шаблоне базы нет: первый раз её добавляет рецепт `database.md`.

### client — `internal/client/**`

- Пакет `internal/client/<provider>`: обёртка над одним внешним API. Своей бизнес-логики нет — транспорт, сериализация и перевод ответов в типы пакета или `internal/model`.
- `type Config struct` + `New(cfg Config) *Client`; если конфиг может быть неполным — `(*Client, error)` с проверкой в `New`. Значения приходят из `internal/config` через `main.go`, сам клиент env не читает.
- HTTP — `net/http` с таймаутом из конфига; секреты не попадают в логи и ошибки.
- Ошибки провайдера — типизированные (`type APIError struct{Code int; Text string}` + хелпер `IsCode`), чтобы сервис или usecase мог ветвиться.
- Локальная разработка без ключей — `internal/client/<provider>/stub`: тот же метод, пишет в лог и отвечает успехом. Выбор stub/реальный — по переменной `<X>_PROVIDER` в `main.go`; stub запрещён в production через `config.Validate`.
- Тест — `client_test.go` с подменой `http.Transport`: проверяем запрос и разбор ответа, сеть не трогаем.

## Миграции — `migrations/**`

- Файл `migrations/NNNNN_название.sql` со следующим номером (`00001_create_orders.sql`, дальше `00002_...`): `make migrate.create name=...` или руками.
- Схему меняют только миграции. Применяет их образ `migrator` перед каждой выкаткой, сам сервис миграций не запускает; если миграция упала, панель оставляет сервис на прежней версии и показывает лог.
- Только вперёд: раздел `-- +goose Down` не пишется. Ошибку в применённой миграции исправляет следующая.
- Формат goose: `-- +goose Up`, затем `-- +goose StatementBegin` … `-- +goose StatementEnd`.
- Каждая миграция идёт в транзакции. Команды, которые Postgres в транзакции не выполняет (`CREATE INDEX CONCURRENTLY`), запрещены: упавшая миграция оставила бы след.
- Миграция проходит на старой версии кода: пока она идёт, работают прежние процессы. Удалить колонку — две выкатки: сначала код перестаёт её читать, потом миграция удаляет.
- Одна таблица — одна миграция. ENUM-тип живёт в миграции таблицы, которая его использует. Связанные таблицы — разными файлами в порядке FK.
- Ключ — `bigserial PRIMARY KEY` (uuid только для публичных непредсказуемых id); время — `timestamp NOT NULL DEFAULT NOW()`; закрытые наборы значений — `CREATE TYPE ... AS ENUM`, а не boolean и не varchar.
- Индекс заводим под конкретный запрос и пишем над ним одну строку, какой запрос он обслуживает.
- Новая колонка на существующей таблице — `NULL` или с `DEFAULT`, чтобы миграция прошла на живых данных.

## paas.toml

Панель читает файл на коммите раскатываемой версии: что в нём написано, то и работает на сервере. Сборка проверяет его той же программой, что панель: с ошибкой образы не соберутся. Проверка локально — рецепт `check.md` скила.

- Неизвестный ключ — ошибка. Ключи — строчными, как в файле шаблона.
- `name` равен имени репозитория, не меняется. `description` — одна строка о сервисе, её видно в панели.
- `[service]`: `replicas` от 1 до 10 (по умолчанию 1), `size` — `small`, `medium` или `large` (по умолчанию `small`; лимит памяти 128, 512 и 2048 МиБ на копию). Две копии переживают перезапуск одной без простоя.
- `[postgresql]`: `enabled = true` — при раскатке сервис получает базу и `DATABASE_DSN`, применяются миграции. Выключение не удаляет базу с данными. `version` — самая старая версия Postgres, с которой работает код.
- `[env_vars]`: имя — латинские буквы, цифры и `_`, не с цифры. Значение всегда строка в кавычках: со значением — обычная переменная, видна в панели; `""` — секрет, значение вводят в панели. `DATABASE_DSN`, `BACKEND_URL` и `APP_PORT` объявлять нельзя. Переменная в файле и поле в `internal/config` появляются одним коммитом.
- `[[workers]]` и `[[crons]]`: `name` совпадает с папкой в `cmd/workers/` или `cmd/cron/`; имя — строчные латинские буквы, цифры и дефис, с буквы, от 2 до 40 знаков, без повторов. `description` — до 120 символов. Запись без папки — ошибка.
- Воркер работает, только если у записи `enabled = true`; есть `replicas` и `size`. Папка без записи — ошибки нет, но воркер не запущен, панель показывает его выключенным.
- Крон: у каждой папки `cmd/cron/<имя>` обязательна запись. `schedule` — пять полей cron в UTC (`"0 3 * * *"`); `@every` и `TZ=` не поддерживаются. Без `enabled` крон включён, `enabled = false` — не запускается по расписанию. Есть `size`, копий нет. Если прошлый запуск ещё идёт, следующий пропускается.

## Процессы: API, воркеры, кроны

- Каждый процесс — свой `main.go` с той же сборкой зависимостей, что в `cmd/api`; бизнес-логика — в service и usecase, а не в `main.go`. Код, общий для API и воркера, живёт в `internal/`.
- Контекст — `signal.NotifyContext(ctx, SIGINT, SIGTERM)`. По SIGTERM процесс заканчивает текущий шаг и выходит за несколько секунд: так выкатка новой версии идёт без потерь.
- Воркер — бесконечный цикл с `select` по `ctx.Done()` и тикеру или очереди. Ошибка одного круга пишется в журнал, воркер не падает: упавший процесс панель перезапускает, и он выглядит сломанным. Интервал — именованная константа с комментарием-«почему».
- Крон — один проход и выход. Код выхода 0 — запуск удался, не 0 — упал, панель показывает это в истории запусков. Проход идемпотентен: если запуск пропущен или повторён, данные не ломаются.
- Воркеру и крону ручки не нужны: `/health` и порт 8080 только у API.
- В шаблоне воркеров и кронов нет. Образцы — `_examples/worker`, `_examples/cron`. Локально — `make run.worker name=<имя>`, `make run.cron name=<имя>`.

## База

В шаблоне базы нет. Её добавляют рецептом `database.md`, когда она понадобилась, — образец в `_examples/postgres`.

- `DATABASE_DSN` задаёт панель, только если в версии `[postgresql] enabled = true`.
- Код, который работает с базой, требует `DATABASE_DSN` в `config.Validate`: без адреса процесс не стартует и пишет «DATABASE_DSN is empty: enable [postgresql] in paas.toml and roll out the version». Раскатка падает с этим текстом, прежняя версия продолжает работать.
- Режима «работаю без базы» (`nil`-репозиторий, ответ 503) не делаем.

## Журнал и секреты

- Журнал — `internal/util/logger`, в стандартный вывод, панель показывает его на странице сервиса: `log.Info(ctx, "notes counted", "count", n)`, `log.Warning(...)`, `log.Error(ctx, err)`. Сообщение — короткое по-английски, данные — парами «ключ, значение».
- Секреты (пароли, токены, ключи, `DATABASE_DSN`) не попадают в журнал и тексты ошибок.
- Настройки — только через `internal/config`: другие пакеты env не читают.
