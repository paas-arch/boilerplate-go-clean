# Слой usecase

- Пакет `internal/usecase/<verb_noun>` (глагол первым: `create_note`, `send_message`): `deps.go`, `usecase.go`, `usecase_test.go`, `_mocks/`.
- Usecase — оркестрация других слоёв, чаще всего сервисов. Собственной логики хранения или работы с SQL/HTTP в нём нет.
- `type Usecase struct` + `New(...)` + единственный публичный метод `Run(ctx, ...)`. Больше трёх входных значений — структура `<Usecase>Params` в `internal/model/<verb_noun>.go`, не в пакете usecase: иначе вызывающий слой импортирует конкретный usecase ради типа.
- Каждое крупное действие в `Run` предваряет нумерованный комментарий-шаг: `// 1. Проверяем текст`, `// 2. Сохраняем заметку`.
- Сначала валидация, которая не ходит в базу и внешние API (trim, длины в рунах, формат), потом вызовы сервисов. Лимиты — именованные константы с комментарием-«почему».
- Каждая ошибка наружу — `errx`: `Validation`/`NotFound`/`Forbidden` с `WithPublicMessage("<по-русски>")` для клиента, `errx.Internal(err)` для всего остального. Sentinel сервисов (`errors.Is(err, <svc>.ErrXxx)`) переводятся в `errx` здесь.
- Один публичный текст на случаи, которые нельзя различать снаружи (чужое/несуществующее), — иначе ручка становится оракулом перебора.
- Запись в несколько таблиц — в одной транзакции: `tx.Do(ctx, func(ctx context.Context) error {...})`, менеджер транзакций собирается в `main.go`.
- Зависимости в `deps.go` называются по роли: `notebook`, `<name>Client`, `logger`. Логгер — только если usecase глотает ошибку (best-effort шаг).
