# CLAUDE.md

Инструкции для ИИ-агента, который дописывает этот сервис. Язык общения и текстов для людей — русский.

## Что это

Бэкенд на Go, созданный из шаблона `go-backend` панели paas. Панель собирает его, по запросу выдаёт ему базу Postgres и выкатывает на сервер. Код — твой: пиши свои ручки, воркеры и миграции. Пример в шаблоне — заметки (`notes`): замени его своим.

## Договор с панелью — не нарушай

Панель выкатывает сервис, не читая код, по этим соглашениям. Если их сломать, сборка или выкатка упадёт.

- **`paas.toml` — настройки сервиса на сервере.** Число копий, размер, база, переменные, воркеры и задачи по расписанию задаёт только этот файл; панель читает его при раскатке. Неизвестный ключ — ошибка: сборка проверяет файл и с ошибкой не соберёт версию. `name` не меняй: он равен имени репозитория. Формат и пояснения — комментарии в самом файле.
- **Не меняй `Dockerfile` и `.github/workflows/release.yml`.** По ним каждый пуш в `main` собирает образы `ghcr.io/<организация>/<репо>/api`, `/workers/<имя>` и `/migrator` с одним тегом версии.
- **В `cmd/` только `cmd/api` и `cmd/workers/<имя>`.** Новый воркер — новая папка `cmd/workers/<имя>` с `main.go`; имя — строчные латинские буквы, цифры и дефис. Панель увидит его сама при следующей выкатке; копии и размер воркера задаёт запись `[[workers]]` в `paas.toml`. Других папок в `cmd/` не заводи: их никто не запустит.
- **Порт — из `APP_PORT`, адрес базы — из `DATABASE_DSN`.** Не переименовывай эти переменные и не задавай порт в коде.
- **Сервис работает и без базы.** Пустой `DATABASE_DSN` значит, что базу сервису в панели не подключали. Процессы стартуют, а то, чему нужна база, отвечает 503 с текстом «База данных не подключена: подключите её на странице сервиса в панели», как ручки примера (`notebook.ErrNoDatabase`). Процесс без базы пишет об этом одно предупреждение при старте, а не на каждом шаге: повторы в логах выглядят как сбой. Миграции без базы не запускаются, их применит раскатка после подключения.
- **`/health` отвечает 200, пока процесс жив.** Он встроен в `internal/util/webserver`; не убирай его и не занимай этот путь.
- **Миграции — в `migrations/`, только вперёд.** Они применяются перед каждой выкаткой, пока ещё работает прежняя версия кода. Правила — `.claude/rules/migrations.md`.
- **Ручки API — под `/api/`.** Веб-приложение проекта пересылает бэкенду только такие пути.
- **Остановка по сигналу.** Процесс завершается по SIGTERM за несколько секунд: так панель выкатывает новую версию без потерь.
- **Логи — в стандартный вывод.** Панель показывает их на странице сервиса. Значения секретов в логи не пиши.

Свои настройки (ключи внешних сервисов и т.п.) добавляй переменными окружения в `internal/config` и тем же коммитом объявляй в `[env_vars]` файла `paas.toml`: со значением — обычная переменная, с пустой строкой — секрет, его значение вводят в панели. `APP_PORT`, `DATABASE_DSN` и `BACKEND_URL` задаёт панель, в файле их не объявляй.

## Команды

- `cp .env.example .env && make db.up migrate.up` — локальная база с миграциями.
- `make run` — API на `:8080`; `make run.worker` — воркер-пример, `make run.worker name=<имя>` — другой.
- `make test`, `make lint` — тесты и линтер; то же проверяет CI на каждый пуш.
- `make codegen` — после любой правки `api/schema.yaml`: пересобирает `internal/generated/`.
- `make generate` — моки после правки любого `deps.go`.
- `make migrate.create name=<snake>` — новая миграция.

## Как устроен код

- Поток вызова `handler → usecase → service → repository → Postgres`; правила каждого слоя — в `.claude/rules/`, пошаговые рецепты — скилы `new-handler`, `new-usecase`, `new-service`, `new-repository`, `new-migration`, `new-client`.
- Контракт API задаёт только `api/schema.yaml`; код ручек и DTO из него генерируется.
- Подробности и разделы, которые обновляются вместе с кодом, — `ARCHITECTURE.md`.

## Комментарии в коде

- Комментарий — одна строка. Объясняем «почему», а не «что». Исключение — нумерованные шаги в usecase.
